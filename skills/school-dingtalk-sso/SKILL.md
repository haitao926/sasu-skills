# 学校钉钉工作台免登与账号关联

先查阅钉钉接口要求，再检查目标应用的登录流程、用户主键、管理员账号和开户政策。目标应用验证钉钉身份、关联本地用户并建立自己的会话。[钉钉官方文档](references.md)

## 接入与账号绑定

1. 与钉钉管理员确认 `corpId`、应用归属的开发者企业账号、企业内部网页应用配置、首页地址、必要权限和发布可见范围。将 `Client Secret` 置于受控服务端配置，前端只使用 `corpId` 和 `Client ID`。从获准的试点成员开始。
2. 在工作台调用 `dd.requestAuthCode({ corpId, clientId })`，通过 HTTPS POST 把一次性授权码交给后端。后端用目标应用凭证获取访问令牌，按应用缓存，并用令牌和授权码换取身份。仅采信钉钉成功响应中的有效身份字段。`result.unionid` 用于本地绑定，`result.userid` 用于查询该组织内的通讯录成员。账号绑定和授权仅使用服务端核验的数据。日志仅记录必要的诊断信息，省略授权码、令牌和密钥。
3. `unionid` 的作用域为开发者企业账号。同一个 `corpId` 下的应用也要核对各自开发者归属。用目标应用凭证和获准的试点成员核验身份，在绑定键中记录提供方、已核验的身份作用域和 `unionid`。凭证或归属变化时复验映射。分别处理 `unionid`、`userid` 和 `associated_unionid`。
4. 在首次免登或自动开户前，按获准的学校名册及稳定标识预绑定到既有本地用户主键，或由用户先登录既有账号再主动绑定。先预演并统计待绑定、已绑定、缺失和冲突的数量。仅凭姓名匹配的记录交由人工核实。名册和成员标识留在受控环境。
5. 用唯一约束、事务和并发控制保证同一作用域内的钉钉身份只关联一个本地账号。同一配对重复提交应安全返回，跨账号占用进入人工核查。若已有重复账号，先确认所有权、数据和额度，再按授权处理。
6. 使用绑定的原本地用户 ID 建立会话，保留账号状态检查、2FA、协议同意、角色、额度和业务数据。保留管理员的原登录方式，将其排除在普通用户的自动绑定和开户流程之外。开户政策允许时才为新用户创建账号，使用目标应用的默认角色和额度。普通浏览器或免登失败时显示原登录入口。

## 按角色或部门授权（可选）

- 使用免登响应中服务端核验的 `userid` 查询成员详情。请钉钉管理员授予「成员信息读权限」，并将试点成员纳入应用获准的通讯录范围。上线前用目标应用令牌确认所需字段可读。[查询用户详情](https://open.dingtalk.com/document/orgapp-server/query-user-details.md)
- 用 `role_list` 中各项的 `id` 和 `dept_id_list` 中的部门 ID 匹配本地明确配置的权限，按组织限定规则。角色名、部门名和 `title`（职位）用于展示。先明确多角色或多部门命中规则时的合并方式。钉钉管理员标记仅供组织管理参考，本地管理员权限由目标应用独立审批和授予。
- 在每次免登时重新评估同步授权，并按目标应用的权限时效要求刷新会话内的权限。成员离职、移出范围或失去对应角色或部门后，撤销对应的同步权限。查询失败或结果无法校验时，暂停依赖该数据的授权，并按目标应用原有策略提供登录回退。保留本地独立授予的权限来源，以便准确撤销同步权限。

## 验证与上线

- 写入前备份相关绑定数据并验证恢复路径。先试点再扩展可见范围，记录关闭免登入口、恢复受影响绑定和处理上线后新增数据的办法。
- 在实际钉钉移动端验证工作台入口，面向桌面客户端发布时也验证桌面端。覆盖首次免登入原账号、重复开户与并发冲突、过期或重复授权码、身份作用域不符、可见范围外成员、2FA、协议同意及原登录回退。启用权限映射时，验证匹配、查询失败和权限撤销。
- 汇报部署状态、预绑定统计、验证结果、待处理冲突和回滚方式，省略个人身份和凭证。
